Because no Commit is involved the leaver is still cryptographically present at that epoch and processes its own announcement like everyone else, so `removedLocally` covers `Remove` only. **Phase 2:** the active owner commits the `Remove` that actually evicts the leaves and rotates the epoch, moving the member to `removed`. | [ADR-041](041-fork-ordering.md) | Same-revision fork ordering by ungrindable precedence, authority, and signer identity | Closed by [ADR-075](075-pairwise-groups.md) (2026-09-13) | 2026-08-17 | [ADR-038](038-fork-convergence.md) ordered siblings by the control state hash alone. That hash is SHA-256 over the signed descriptor, and the descriptor's 16-byte event id is free author-chosen entropy that nothing binds, `created_ms` is an unvalidated `u64`, and Ed25519 is deterministic, so one grinding trial is one signature plus one hash and produces an independent uniform ordering value. Measured on the shipped signing path: about 24,500 candidate branches per second per core, and 9 trials to land below one known rival. A member facing eviction sees the `Remove` first, so it could undercut it for well under a millisecond of work and quarantine the evicting owner instead. Ordering now reads the operation's precedence class first, so an eviction cannot lose to a metadata edit, an invite, or a leave; then the signer's role in the reconstructed shared parent, so an evicted admin's counter-`Remove` loses to the owner's; then the authenticated signer identity. The hash is reached only between two branches from one device, where ordering decides nothing that author could not decide by choosing which branch to send. Every input is either fixed by the shared parent or bound to an authenticated device credential, so no participant can bias the outcome, and the rule stays total, deterministic, server-independent and free of extra round trips. ## Disposition of Legacy Non-ADR Sections

The legacy monolithic `frontend/docs/decisions.md` ended with two non-ADR headings (`## Dependency opinion` and `## Decisions that do not block development`). Their durable ownership is routed as follows:

- **`Dependency opinion`** (replaceable adapters, never letting a package model become the product protocol, and pinning versions after platform spikes):
  - Architectural adapter and protocol boundary: owned by [OVERVIEW.md](../OVERVIEW.md), [ADR-006](006-forui-boundary.md), and [ADR-066](066-sliver-timeline.md).
  - Exact package version selection and lockfile/supply-chain pinning: owned by [RELEASE.md](../../runbooks/RELEASE.md) and [ADR-054](054-dependency-policy.md).
- **`Decisions that do not block development`**:
  - *Placeholder product name, logo, and app icon vs. frozen Android application IDs:* owned by [DESIGN-SYSTEM.md](../../ui/DESIGN-SYSTEM.md) (brand assets still expected), [RELEASE.md](../../runbooks/RELEASE.md), [ADR-067](067-serving-origin.md), [ADR-075](075-pairwise-groups.md), and [ADR-076](076-production-signing.md) D8 (Android application display label `"Communication Platform"`).
  - *Direct signed APK initial release channel vs. post-v1 Web:* owned by [RELEASE.md](../../runbooks/RELEASE.md), [STATUS.md](../../STATUS.md#the-web-target), [ADR-033](033-android-release-target.md), [ADR-075](075-pairwise-groups.md), [ADR-076](076-production-signing.md), and [server ADR-0020](../../../../docs/architecture/decisions/0020-one-android-client-and-no-browser-surface.md).
  - *Django Admin remains the administration surface; a client admin feature is out of scope:* server administration is owned by [PANEL-RECORD.md](../../../../docs/admin/PANEL-RECORD.md) and [server ADR-0011](../../../../docs/architecture/decisions/0011-django-unfold-admin-panel.md); no client admin feature exists in `frontend/`.
