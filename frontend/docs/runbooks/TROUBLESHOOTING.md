# Field and operator troubleshooting

This runbook covers field and build-triage symptoms for the Android client
(`com.orviniq.chat` production, `com.orviniq.chat.development` local engineering). Every
check and recovery step preserves local cryptographic state and trust enforcement.

## Non-negotiable field rules

- **Never delete user data to recover.** Uninstalling the app, clearing app storage, or
  deleting the SQLCipher database, `noBackupFilesDir/storage_key_v1.bin`, or the
  `AndroidKeyStore` wrapping key (`ProtectedStorageChannel.kt`) permanently destroys message
  history, ratchets, and device state. The server holds no message-history backup, and
  `allowBackup="false"` disables Android backups ([SIGNING.md](SIGNING.md#what-is-at-stake)).
- **Never run `adb install -d` or Flutter install/run/drive against a signed production
  install.** Use `adb install <apk>` for first install or `adb install -r <apk>` for
  in-place updates ([SIGNING.md](SIGNING.md#installing-on-a-device)).
- **Never bypass TLS or identity verification.** `TransportSecurity.provisioned` anchors
  `dart:io` exclusively to the compiled-in private CA (`SecurityContext(withTrustedRoots: false)`
  with `badCertificateCallback` returning `false`). Never add certificate exceptions,
  system-root fallbacks, STUN/public ICE servers, or unverified-peer bypasses.
- **Never run `backend/ops/tls/make_ca.sh` during release or field triage.** It mints a
  new `server.key` and invalidates provisioned primary SPKI pins ([SIGNING.md](SIGNING.md#1-derive-the-provisioning-values-afresh-for-every-build)).

## Safe first export: user-initiated diagnostics

Ask the user to open **Settings → About → Diagnostics report**
([DiagnosticsPage](../../lib/features/diagnostics/presentation/diagnostics_page.dart)) and
copy the report. By construction ([DiagnosticsReport](../../lib/features/diagnostics/domain/diagnostics_report.dart)):

- The export is locale-independent ASCII grouped into `[application]`, `[device]`,
  `[storage]`, `[delivery]`, and `[network]`.
- Values are strictly enums, flags, clamped integers, compile-time constants, UTC-hour
  timestamps, or bucketed quantities (`0`, `1-9`, `10-99`, `100-999`, `1000+`).
- It contains **no** message text, usernames, display names, server origins, keys, tokens,
  or device/conversation identifiers, and is copied only to the clipboard—never uploaded
  automatically.

## Symptom table

| Symptom | Safe first check | Observable result | Permissible recovery | Escalation point |
|---|---|---|---|---|
| **Failed provisioning** | Read the blocking bootstrap screen (`BootstrapPage`); on a release host, verify the 5 `PRODUCTION_*` env vars and run `tool/verify_release_apk.sh --production <apk>`. Compare live `openssl s_client` primary pin with `PRODUCTION_PRIMARY_SPKI_SHA256`. | Device shows **"App not provisioned"** (`ConfigurationNotProvisioned` for missing/malformed origin, CA SHA-256, primary/backup SPKI pins, duplicate pins, or missing/invalid `PRODUCTION_PRIVATE_CA_PEM_BASE64`) or **"Server trust could not be verified"** (`trustFailureTitle` when `dart:io` rejects the server cert against `SecurityContext(withTrustedRoots: false)`). Build host stops with `Missing production provisioning`, `PRIMARY PIN MISMATCH`, or CA mismatch/expiry. | Re-derive all five `PRODUCTION_*` values afresh from `backend/ops/tls/out/` ([SIGNING.md](SIGNING.md#1-derive-the-provisioning-values-afresh-for-every-build)), rebuild with `tool/build_production_release.sh --build-number <higher-N>`, verify with `tool/verify_release_apk.sh --production`, and update in place with `adb install -r <apk>`. | Escalate to the deployment/TLS operator if `openssl s_client` serves an unexpected SPKI pin, if the private CA expired or rotated unexpectedly, or if a properly provisioned build fails `trustFailure` against the live host (see open runtime SPKI pinning decision in [ADR-076](../architecture/decisions/076-production-signing.md) D7). |
| **Expired or revoked sessions** | Read the auth/login banner (`authSessionExpiredMessage` vs `authRevokedMessage`); if still signed in, inspect Diagnostics `[delivery]` (`session=...`) and `[network]` (`backend_rejected`, `most_failed_operation`), and check device wall clock. | **Expired (`SessionTerminationReason.expired`):** `POST /api/v1/auth/renew` or an authenticated call returned `401 invalid_token`, or a 10-minute `register`-scope token expired before `POST /me/devices` completed (`TokenCoordinator` renews `full` tokens from half-lifetime and forces wait in the final 2 min + 30 s skew window). UI shows *"Your session has expired. Log in again."* **Revoked (`SessionTerminationReason.revoked`):** REST `401 token_revoked` or WebSocket close `4003`; local Keystore key, DB, and `secure_attachment_cache` are wiped (`ProtectedStorageChannel`), and UI shows *"This session is no longer valid. Local data from this installation was removed."* Transient offline/`5xx`/`429` failures during early renewal pause retries for 1 minute and keep the session alive. | For **expired** sessions: correct device clock if drifted, sign in again, and complete device reconciliation (`enrollmentAmbiguousTitle` if a registration response was lost) or re-link. If a local database remains after expiry without revocation, follow the app's sign-in/re-auth flow rather than uninstalling; if all devices are lost, restore identity with the recovery secret (history is not in the identity backup). For **revoked** sessions: re-enroll a new device only if the account remains active and authorized, using an existing cross-signed device or the recovery secret. | Escalate to the operator/account owner if `token_revoked` or close `4003` happened without user revocation or account erasure (possible security event or account deactivation), or if re-login / `POST /api/v1/auth/renew` fails with `401` when credentials and device clock are valid. |
| **Held first messages** | Open **Chats** and look for a held-sender row (`chatsHeldSenderLine`: *"`<sender>` sent you `<N>` message(s). Verify to read..."*). On the sender side, look for `chatUndeliveredHint` under an unacknowledged direct message after 1 hour. In Diagnostics `[storage]`, check `held_inbound`. | `held_inbound` is non-zero (`1-9`, etc.) while `pending_inbound` excludes held rows. In `PairwiseOpaqueEnvelopeInspector`, an initial envelope from an `unverified` sender matching an unverified live device is stored in `inbox_envelopes` state `5` (`held`), followed by regular envelopes on that `held_session_id`. Hold caps are 64 envelopes per sender, 128 per phone, and 7 days from `held_at` (evicted/expired rows move to `quarantine`, increasing `quarantined_input`). Master-key changes and device-log forks are **not** held (`safetyMasterChangedState` / `safetyForkState`). | Tap the held-sender row (or open the contact's **Safety number** screen), compare the `CP-SAFETY-V1` value out of band with the sender, check *"I compared the values out of band with this contact"*, and tap **Confirm verified**. `PeerVerificationObserver` and `DurableSyncEngine._maintainHeldEnvelopes` release held rows in mailbox order without re-fetching from the server. Never confirm verification without an actual out-of-band check. | Escalate or re-verify out of band if the contact shows `safetyMasterChangedState` or `safetyForkState`, or if held messages exceeded the 7-day window or 64/128 caps (`quarantined_input` rose; quarantined envelopes cannot be opened and must be re-sent by the peer after verification). |
| **Mailbox gaps (`pruned_through`)** | Check Diagnostics `[delivery]` for `queue_gap_detected=yes`. Inspect **Group Info / Group Chat** (`groupQueueGapState` / `groupWithheldQueueGap`) and **Voice Room Info** (`voiceRoomStateWaiting` / `voiceRoomWaitingNotice`). | `DriftSyncStore.persistDrainPage` saw `last_acked_seq < pruned_through` (server envelopes expired past `ENVELOPE_TTL_DAYS`, 7 days default). Active groups enqueue `group_state_requests` and withhold sends/changes; active rooms set `RoomLifecycle.stateRecoveryRequired` and withhold calls, invites, renames, and leaving. `DurableSyncEngine` continues draining newer envelopes and sends authenticated repair + state requests in role order (owner, admins, members; next member after 6 hours). **Known gap ([STATUS.md](../STATUS.md#platform-identity-and-content)):** 1:1 direct chats show no direct-gap UI (`SyncProjection.isSecurityBlocked` has no UI consumer) and lack a bulk pairwise-session repair sweep. | Keep the device online so authenticated pairwise repair and signed `CPGSV001` / `CPVRV001` transcript responses complete. Ask an active group/room member to open the app briefly to answer the state request (a room with no other active member stops waiting). For missed 1:1 content: pruned server envelopes cannot be recreated; ask peers to re-send missed items or use device-to-device history transfer from another online own device (content only, not ratchets/control state). | Escalate if `queue_gap_detected=yes` persists after active group/room members have been online across multiple 6-hour retry intervals, if state recovery uncovers a conflicting chain (`groupForkState` / `voiceRoomConflictNotice`, which requires out-of-band resolution or a new group/room), or if a 1:1 session stays stuck after peer repair. |
| **Unavailable voice** | Check the **Voice Rooms** / **Voice Room Info** / pre-join error message and Diagnostics `[network]` (`backend_rejected`, `transport_failed`). | Distinct states in `RelayCredentialService`, `VoiceCallEngine`, and `VoiceCallController`: (1) `voice_configured=false` or `503 voice_unconfigured` → **"This server does not offer voice"** / **"Voice is not set up on this server"** (persists for process life); (2) `429 throttled` → **"Too many attempts"** with `Retry-After` countdown (or 1 min fallback); (3) `credentialFailed` → network error, `5xx`, or rejected non-`turn:`/`turns:`/empty/>16 `urls`; (4) room `stateRecoveryRequired` / fork / left / removed → join refused before mint; (5) `RECORD_AUDIO` denied or foreground `VoiceCallService` refused / app backgrounded → join aborted before sending; (6) 10 joined devices reached → **"This call is full"** (`VoiceCallCeiling.maximumJoinedDevices`); (7) single peer tile **"Not reachable"** (~20 s after 4 attempts at 0/2/4/8 s + 6 s window, or missing durable session `noSession`), **"Safety number changed"**, or **"Needs a newer app"**. | For `503` after operator fixes server: restart the app process so `RelayCredentialService._refusedByServer` clears. For `429`: wait out the cooldown timer. For mic denial: grant Microphone via **Open settings** and join while the app is foregrounded. For waiting/conflicted rooms: wait for `CPVRV001` recovery or settle fork out of band. For a single peer **Not reachable**: tap **Try again** on their tile once they are online and durable `CPVRV001` session-start completed; for **Safety number changed**: re-verify out of band. Never add STUN or public ICE servers. | Escalate to the server/coturn operator if `POST /api/v1/me/relay` returns `503 voice_unconfigured`, invalid/`turns:` URLs, or `5xx`, or if credential minting returns `200 OK` yet **every** peer fails to connect (coturn unreachable, UDP/TCP relay ports blocked, or shared-secret/clock drift). Note ([STATUS.md](../STATUS.md#voice-implementation-gaps)): a distinct "all-candidate-pairs-failed after 15 s" relay-unreachable banner is not yet built. |
| **Background delivery** | Open **Settings → Receiving while closed** (`sustained_delivery_page.dart`) and **Settings → Notifications**; inspect Diagnostics `[delivery]` (`notifications=...`, `sustained_delivery=...`, `delivery_session=...`). On test devices with `adb`, run `tool/measure_sustained_delivery.sh probe` or inspect `dumpsys activity services` / `am get-standby-bucket` / `dumpsys deviceidle whitelist`. | **Default floor (`DeferredDeliveryJobService`):** ≥15 min `JobScheduler` cadence, deferred by Doze, disabled in `rare`/`restricted` standby buckets (Android 13+ after 8 days unused), blocked under Data Saver, stopped by Force Stop. **Opt-in `SustainedDeliveryService` (`specialUse`, `bestEffort` per ADR-094; gate CLOSED):** Settings reports exact state—`Off`, `On` (`Kept open in the background` persistent `VISIBILITY_SECRET` notice), `alertsWithheld` (notifications off), `exemptionWithdrawn` (battery exemption revoked, e.g., after OS update), or `stopped` (killed by OEM/OS or awaiting 15 min job recovery after reboot/update). Alerts post `New message`/`New messages` only for committed unread rows (muted or foreground-visible chats suppress alerts). | If `alertsWithheld`: re-enable app notifications (**Turn on**). If `exemptionWithdrawn`: tap **Turn on** in **Receiving while closed** to re-grant `ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`. If `stopped` on Samsung/Xiaomi: tap **Open my phone's settings** and add the app to Samsung *Never sleeping apps* or Xiaomi *Background autostart*, then reopen the app and avoid Force Stop. Do not promise a specific delivery latency (no cell of the sustained-delivery matrix is evidenced). | Escalate with the Diagnostics report (and on test hardware, `tool/measure_sustained_delivery.sh` `probe`/`samples.ndjson`/`verdict` artifacts per [SUSTAINED-DELIVERY.md](SUSTAINED-DELIVERY.md)) if the service exits repeatedly while `doze_exempt=true`, notifications are enabled, and vendor exclusions are set, or if carrier NAT drops the 4-minute WebSocket keepalive. |
