# 0027. The serving origin moves, and a pin moves with it

- Status: Accepted
- Phase: 11
- Date: 2026-09-07
- Landed: 2026-09-07, across three runs of phase 11. `ops/nginx/chat.orviniq.com.conf`
  is the site file and both its server blocks name the new host, `.env.example` and
  `ops/coturn/turnserver.conf` carry the relay values that follow it, the two posture
  tests read the site file by its new name, and the leaf certificate under
  `ops/tls/out/` was reissued for `chat.orviniq.com` against the existing root.

## Context

The serving hostname moved from `chat.nimashadloo.dev` to `chat.orviniq.com`. Nothing
else about the deployment moved with it: same VPS, same architecture, same private-CA
TLS posture, same routes, same ports, same units. All prior data is gone and nothing is
installed anywhere, which is the condition that made the rest of this decision cheap.

A hostname is normally the least interesting thing to change. It is not, here, because
this deployment's TLS trust is not a public CA's. The root generated by
`ops/tls/make_ca.sh` is created once, kept offline, and pre-installed on the devices
that will use the server; the client also SPKI-pins the server key, primary and backup,
and runs with `SecurityContext(withTrustedRoots: false)` so there is no public trust
store underneath to catch a mistake. Three separate things therefore have to be reasoned
about rather than assumed: the root, the leaf, and the pins.

**The easy answer is right about two of them and wrong about the third.** The root is
hostname-agnostic by construction — subject `CN=chat private root CA`,
`basicConstraints=critical,CA:TRUE,pathlen:0`, `keyUsage=critical,keyCertSign,cRLSign`,
no `nameConstraints` and no SAN of its own — so it signs for any name and needs no
reissue. And an SPKI pin covers a public key, not a hostname, so a leaf reissued for a
new name over the same key holds every pin that was ever computed from it.

That second half is true of pinning and false of this repository. `make_ca.sh` is a
first-generation script that has only ever been read as one. It guards the two keys it
means to preserve — `ca.key` and `backup.key` — behind `if [ ! -f ]`, and it mints
`server.key` unconditionally on every run. There is no reissue path in it that keeps a
server key. Running it for the new domain therefore produced a new server key and a new
**primary** pin, and the client-side value that has to match it lives in provisioning,
outside this tree, where nothing in CI can notice it has gone stale.

Against a deployment with installs, that is a permanent lockout of every device, and the
backup pin is the single rotation that ADR-042 bought to survive it. Against this one,
on this date, it costs a re-read.

## Decision

### 1. The origin is `chat.orviniq.com`, and the rename is the whole change

The site file is renamed to the host it configures and both server blocks name it.
`TURN_URLS` and `TURN_REALM` in `.env.example` name the box coturn runs on, and the
realm placeholder in `ops/coturn/turnserver.conf` is the same value in the same shape.
coturn needs no certificate of any kind for this: it runs `no-tls` and `no-dtls`, sets
no `cert=`, `pkey=` or `tls-listening-port`, and is the only media service in the
deployment ([0021](0021-relayed-webrtc-mesh-and-no-server-room.md)).

None of it reaches a running host. nginx serves from its own copy under `/etc/nginx`,
the service reads `/etc/chat/env.production`, and neither is in this tree, so nothing
here asks for a reload, a restart or a redeploy. What moves is what the next install
copies. **One thing a host already deployed has to be told:** the old
`sites-enabled` symlink survives the rename, and installing the new name beside it
leaves two server blocks answering for one host.

`core/tests/test_settings_posture.py` and `config/tests/test_urls.py` read the site file
by name rather than by glob — deliberately, so a rename fails there rather than passing
over an empty match — so both constants moved with the file.

### 2. The root CA is reused, and is the reason this was a small change

The root signs for the new host unchanged. `BETA_PRIVATE_CA_SHA256` and
`BETA_PRIVATE_CA_PEM_BASE64` keep the values they already had, and no device needs a new
trust anchor.

This was verified rather than argued: `ca.crt` and `ca.key` carry their original
2026-08-19 mtimes, the reissue archive holds a leaf pair and no CA, and the fingerprint
read off the current `ca.crt` is the one already provisioned. The root remains valid to
2036-08-16.

### 3. The leaf is reissued, and the primary pin moves with it

The leaf is `CN=chat.orviniq.com`, `subjectAltName=DNS:chat.orviniq.com`, valid to
2028-12-10, signed by the unchanged root.

**The primary SPKI pin moved with the server key, and the backup pin did not.** The
primary is computed from the leaf's public key, which `make_ca.sh` regenerated; the
backup is computed from `backup.key`, which it left alone. Measured off the archived and
the current material rather than inferred: the two primary pins differ, and the backup
key is the same file it was on 2026-08-19.

Neither value is written here. This repository carries no real pin and no real CA
digest — `frontend/docs/release-signing.md` keeps them as placeholders and calls them
public values that stay out of the tree — and that convention is not broken to record a
change to one of them.

The operational consequence is stated plainly because nothing enforces it:
**`BETA_PRIMARY_SPKI_SHA256` must be re-read from the new certificate before the next
client build.** A client compiled against the old primary pin does not degrade or warn
against the new leaf; it fails the handshake closed, which is what the pinning posture is
for. No test in this repository can fail on a stale pin, because the pins are
provisioning values and deliberately absent from it.

**What is not decided here:** whether `make_ca.sh` should grow a reissue path that
preserves the server key. The script is correct for first generation, which is the only
thing it has ever been asked to do. Making it safe for reissue is a change to
provisioning tooling with its own failure modes — an operator who reuses a server key
across a name change also carries that key's age forward — and it is left to the
decision that needs it.

### 4. Every artifact built before this date is superseded

An artifact built before 2026-09-07 carries the old origin, the old application ID, the
old signing certificate and the old primary pin. Any one of the four disqualifies it,
and the last means it cannot reach the server at all. None may be distributed.

The client half of this — the application IDs moving to
`com.orviniq.chat{,.beta,.development}` and the Beta signing identity being reissued
under a matching subject — is `frontend/docs/decisions.md` ADR-067, which supersedes
ADR-042. It is recorded there rather than here because it is client identity, build and
distribution, and this register holds deployment-wide posture.

## Position fields

- **Forcing function.** A hostname change against a private-CA deployment touches three
  things that are usually one. Two of them needed nothing. The third — the primary SPKI
  pin — moved silently, because the only tool that issues a leaf also mints a server key,
  and the value that has to track it lives outside this repository where no test reads
  it. The migration landing on a day with zero installs is what turned that from an
  incident into a note.
- **Scale band.** Band 0, holding through band 2, and unchanged by this decision. A
  hostname is not a load-bearing quantity: the site file, the relay values and the
  provisioning examples cost the same at 20 devices and at 500.
- **Flip trigger.** For the reused root: its 2036-08-16 expiry, or a decision to
  constrain it by name, either of which makes it a new anchor to distribute. For the pin
  posture: the first external install, after which a server-key change is no longer a
  re-read but a rotation onto the backup pin — the one rotation that exists. For
  `make_ca.sh`: a second reissue, at which point doing this by hand twice is worse than
  the tooling change decision 3 declines to make.
- **Cost.** The rename costs an operator step that no test can check — removing the old
  `sites-enabled` symlink on a host that already has one — and it costs the re-read of
  `BETA_PRIMARY_SPKI_SHA256` before the next build. The leaf reissue costs the primary
  pin's rotation budget: a deployment gets one safe server-key change per backup pin, and
  this one spent nothing only because no client held the old value. It costs nothing in
  handshake, cipher, route, port or unit terms, because none of those moved.
- **Evidence.** The CA reuse and the pin movement were both measured on this run rather
  than assumed, off the archived and the current certificates: the root's subject,
  expiry and fingerprint unchanged with 2026-08-19 mtimes on `ca.crt` and `ca.key`; the
  archive holding a leaf pair and no CA; the new leaf's subject and SAN reading
  `chat.orviniq.com`; the two primary pins differing and the backup key untouched. **What
  is not evidence:** nothing here has been served. No nginx has loaded the new leaf, no
  client has completed a handshake against it, and the claim that a stale primary pin
  fails closed is read off the posture rather than observed. **Currency:** current.

## Consequences

- ADR-042 in `frontend/docs/decisions.md` is superseded by ADR-067. Its reasoning is
  untouched; only its premise failed, and the frozen-identity rule it establishes
  re-binds from this date.
- ADR-044 in the same register gains an amendment line. Every identifier it names reads
  as migrated; every decision it makes stands.
- `BETA_PRIMARY_SPKI_SHA256` is stale in any provisioning environment that predates this
  decision. It is the only claim in this run that no test can fail on, and it is written
  down for that reason.
- `ops/tls/make_ca.sh` regenerates `server.key` on every run. That is correct for first
  generation and wrong for a reissue, and it is why the primary pin moved. The script is
  unchanged by this decision.
- The old `sites-enabled` symlink survives the rename on any host already deployed.
  Removing it is an operator step, enforced by nothing in this repository.
- `ops/tls/README.md` still describes coturn as pointing at `/etc/letsencrypt/live/`.
  coturn terminates no TLS ([0021](0021-relayed-webrtc-mesh-and-no-server-room.md)), so
  that sentence describes a dependency the deployment does not have. It predates this
  decision and is not corrected by it.
